# Client protocol

The server exposes HTTP and WebSocket endpoints on one origin. The browser uses the same origin for both. A mobile client can use the same JSON messages over `/ws`.

## Create and join

Send `POST /api/boards` to create an empty board with three default columns. The response is `201 { "id": "..." }`.

Open `/ws`, then send a join within ten seconds:

```json
{ "type": "join", "boardId": "demoBoard", "clientId": "clientAlice", "name": "Alice" }
```

Ids must contain 4–32 ASCII letters or digits. Board ids generated by the server have eight characters. Names are trimmed and capped at 40 characters. Keep one client id stable across reconnects. Use distinct client ids for independent editing sessions.

Omit `sinceVersion` for a full snapshot. Include it only when the client has the matching confirmed state. The server responds with a `snapshot` or `ops` with `catchup: true`. An empty catchup means the stored version is already current. A second join on a connected socket requests a full snapshot of its current board.

## Submit an intent

```json
{
  "type": "op",
  "opId": "clientOp01",
  "baseVersion": 4,
  "op": { "type": "moveCard", "cardId": "cardAlpha", "toColumnId": "doneColumn", "toIndex": 0 }
}
```

Generate a new op id for each intent. Preserve that id and its intent on retry. `baseVersion` records the version known to the client; it is not a compare-and-swap lock. The server validates against current state and serializes accepted operations in arrival order.

The server broadcasts accepted operations:

```json
{ "type": "ops", "ops": [{ "version": 5, "actorId": "clientAlice", "opId": "clientOp01", "op": { "type": "moveCard", "cardId": "cardAlpha", "toColumnId": "doneColumn", "toIndex": 0 } }] }
```

Each accepted operation advances the version by one. Advance confirmed state only in order. If the next version has a gap, request a full snapshot. Card and column positions use remove-then-insert indexing and clamp to the target list bounds.

For a retry already recorded in SQLite, the server responds only to its sender:

```json
{ "type": "ack", "opId": "clientOp01", "version": 5 }
```

An acknowledgement clears the matching pending intent. It does not apply a mutation. The version is the original accepted version, which can be lower than the client's current snapshot. If the acknowledgement is ahead of confirmed state, request a snapshot. Receipts are scoped to the board and client id and commit with the mutation. Reusing an id with a different intent is rejected as `invalid_op`.

## Optimistic state and rejection

Keep confirmed state separate from pending intents. Render confirmed state with pending intents replayed through the mutation rules. On an accepted broadcast from this client, remove its matching pending intent. On snapshot or catchup, resend pending intents with their original ids. On `ack`, drop the acknowledged intent without replaying it on confirmed state.

Rejections contain `type: "reject"`, `opId`, `reason`, and the current `version`. Drop the rejected intent and rebuild the view from confirmed state plus the remaining intents. Valid reasons are `card_not_found`, `column_not_found`, `duplicate_id`, `invalid_op`, and `limit_exceeded`.

## Contract fixture

[sync-contract.json](../shared/fixtures/sync-contract.json) contains an initial board, 11 accepted operations covering all ten mutation types, and the expected final state. Additional clients can run the same fixture through their mutation engine. Compare entities by id and order; array insertion order is an implementation detail.

Presence and cursor messages are ephemeral. They do not affect versions or persistence. The server relays cursor positions in board-content coordinates, which may be approximate across different layouts.
